# Voice guide: how I talk upstream

## Who I am in threads

I am comfortable with Python and am learning this repository's contribution workflow.
I investigate one issue at a time, show commands and output from my environment, and separate what I observed from what I infer.
Readers can expect a claim first and a concrete reproduction report after I run it.

## Rules I write by

### Rule: Name the exact issue

Use the affected function and behavior, so my claim cannot be pasted under a different bug.

- Wrong: "I'd like to work on this issue."
- Right: "I'd like to investigate the top-level JSON array crash in `parse_review_output` for issue #69."

### Rule: Promise investigation, not a result

Before I run a reproduction, name the next test and promise to report what happened. Do not guarantee a fix or a date.

- Wrong: "I reproduced it and will fix this by tomorrow."
- Right: "I'll run the array input and the existing focused test, then report the output before proposing a change."

### Rule: Show what actually ran

Use commands, code state, environment, and output I captured; never turn an expectation or another commenter's result into my own observation.

- Wrong: "The parser definitely crashes on every machine."
- Right: "On the recorded commit and Python version, my direct array call raised `AttributeError` at `_parse_json_output`."

### Rule: Separate evidence from cause

Describe the observed symptom first and label possible explanations as hypotheses until tested.

- Wrong: "The model is broken and causes the parser crash."
- Right: "The array input reached `_parse_json_output`; the traceback shows `.items()` was called on a list."

### Rule: Respect the repository's AI policy

Check the stated contribution rules before posting. If disclosure is required, say how AI helped while taking responsibility for the commands and statements in my comment.

- Wrong: "No AI was involved," when AI helped draft the comment.
- Right: "I used AI assistance to draft this report; the commands and output below come from the recorded run."

## Things I never post

- A promise to finish, fix, or open a PR by a date I cannot guarantee.
- "Same as above" in place of my own reproduction.
- A root-cause claim without matching evidence.
- Output that I did not actually capture from the stated environment.
- A comment that violates a repository's disclosure requirement.

## PR descriptions

- Put the affected behavior in the title; explain the triggering input and resulting behavior in the summary.
- Describe only what the committed diff and recorded tests demonstrate. Keep CI unchecked until the PR's actual checks establish it.
- State a deferred case and why it is deferred without calling the whole original plan complete.
- Disclose the actual assistant (Codex) and its role. Never claim Claude was used, or that I personally reviewed each line unless that review actually happened.

## The question

A pr-precheck tool answers exactly one question about exactly one PR
package: **is this ready to submit?** A PR package is a candidate pull
request (title, description, commits, diff, test evidence), read
against the plan it claims to implement and the issue that plan
belongs to. The tool never answers a different question, never grades
more than one package per run, and never answers from gut feel: it
executes the components in this directory.

## The layout

One fixed layout for the whole cohort, so grading stays uniform and
harness feedback stays signal. Every file sits at exactly this path
inside the tool directory:

    SKILL.md                     the frame: what the tool does, and how
    rubric.md                    the checks and the verdict rule
    procedure.md                 the operating steps
    voice-guide.md               your week-2 voice guide, pasted forward
    scope.md                     where the tool may operate (you fill the Repo line)
    references/
      evidence-guide.md          where evidence lives in a PR package

Nothing about this layout is yours to invent: no extra components, no
renamed files, no relocated references. The harness inlines
`SKILL.md`, `rubric.md`, `procedure.md`, and
`references/evidence-guide.md` from these exact paths; a file
somewhere else does not exist as far as the interface is concerned.
This is the same shape weeks 2 and 3 shipped; what changed is who
writes the contents.

## Modes

The tool runs in exactly two modes, and SKILL.md must define both:

- **Live mode**: the student's own submission, checked before it goes
  out. Inputs: their `plan.md` (deviation notes included), the diff on
  their branch, their draft PR title and description, and their test
  evidence, read against their issue. A house-chain student reads the
  house plan and the house repro pack instead; the same checks grade
  the same things there. Live mode gathers issue-side evidence from
  the real repo (the thread, the PR template, the stated policy).
- **Eval mode**: a package bundle is the whole world. Every fact comes
  from the bundle text; nothing is fetched, nothing else is read. Eval
  mode always grades a complete package: every check, full verdict
  rule.

## Verdict space

Binary: `accept` (ready to submit) or `reject` (hold). There is no
third verdict, no "accept with reservations", no score. Reservations
belong in check evidence lines, not in the verdict.

## Output

The tool's reply ends with a fenced JSON block, and nothing follows
it. The schema is fixed and may not be altered, extended, or
reordered:

```json
{
  "item": "<PR URL or bundle id>",
  "checks": [
    {"name": "<check name>", "grade": "pass|fail|unclear",
     "evidence": "<one line: the fact or quote that decided it>"}
  ],
  "verdict": "accept|reject"
}
```

The harness parses the last fenced JSON block in the output. A
readable per-check summary may come before the block; the block is the
machine-read result and must be present, valid, and last.

## The scope seam

In live mode, the tool reads `scope.md` before anything else. The
scope names where the student's PR must live and the house rules of
that environment; the tool refuses to grade work outside the scoped
repo, and if the scope's repo line still carries an unfilled
placeholder it stops without grading and tells the student to fill
the `Repo:` line in `scope.md` with their section's Path Review repo.
It never guesses a scope. In eval mode, `scope.md` is ignored
entirely. This seam is why the same tool graduates: staff swap one
file and the field of view changes.

## The voice seam

In live mode, the tool also reads `voice-guide.md` (the student's own
rules for how they write upstream, carried forward from week 2) and
holds the outgoing PR text, the title and the description, against
those rules, reporting any rule the draft breaks in the summary. The
voice guide never changes the verdict on its own unless the rubric has
a check that reads it. In eval mode, `voice-guide.md` is ignored
entirely: voice is personal and carries no gold labels; universal
communication-quality checks live in the rubric.

## The refusal rule

A tool with no rubric content or no procedure content refuses to grade
and says so, by design. The shipped templates are empty on purpose; an
empty tool that invents checks at runtime is worse than no tool,
because its verdicts look like judgment and are noise. The instruction
comments inside the templates are guides, not content: the harness
ignores comments when it checks whether a file is still a template, so
keep them or delete them as you fill each file; only your own written
text counts.

## Grading discipline (contract terms)

These are not style advice; they are interface guarantees the master
tool honors and the bar assumes:

- **Evidence first.** No check is graded without naming the fact or
  quote that decided it. "Looks fine" is not evidence.
- **Grade the thing, not the polish.** A terse complete PR can be
  ready and a beautiful confident one can be hiding drift. Every check
  reads the artifact itself against the plan, the issue, and the
  stated standards, never the formatting.
- **The rubric decides, not the run.** If a check passes by its stated
  condition but feels wrong, it still passes; the fix belongs in the
  rubric, not in the run.
- **The procedure decides how, not the run.** The tool follows
  `procedure.md` as written and reports its gaps instead of silently
  inventing steps.
- **Unclear defaults to fail.** Treat `unclear` as the rubric's
  verdict rule directs; where the rule is silent, an unverifiable
  claim is a failing one. A PR you cannot verify from the package is a
  PR that is not ready to submit.

# pr-precheck: rubric-driven PR grading

## The question

Decide one question about one PR package: is this ready to submit? Read its title, description, commits, diff, and test evidence against the plan it claims to implement and the issue that plan belongs to. Grade the submitted change, including its stated limits; do not redesign the project or grade the author's confidence.

## Inputs and modes

Choose LIVE MODE for an actual candidate and EVAL MODE for one frozen bundle. Never mix the modes or grade multiple packages in one run.

In live mode require named paths to `plan.md` including its deviations, `pr_draft.md` with the first line as the title and the remaining text as the description, and `test_evidence.md` with actual commands, outputs, exits, and code state. Read commits with `git log main..HEAD --oneline` and produce the complete committed branch diff from the working copy with `git diff main...HEAD` (three dots). Check `git status --short` and report uncommitted changes that are absent from the graded diff. Verify the base repository/default branch rather than substituting a working-tree diff. Read the issue body and full thread on the real scoped repository, `.github/PULL_REQUEST_TEMPLATE.md`, and `docs/CONTRIBUTING.md`. Record unavailable sources as missing evidence. A house-chain student supplies the designated house plan and house repro pack in place of the personal plan and reproduction; apply the same checks. Use the candidate PR URL as item when one exists; before opening use the candidate's repository compare URL so the output still identifies the actual PR package.

In eval mode the supplied bundle is the whole world. Read its repo facts, issue and thread, accepted plan context and deviations, candidate title/description/commits/diff, and test evidence. Fetch nothing and read no other files, pages, repository, source issue, gold labels, or prior verdict. Execute every rubric check and the full verdict rule. Ignore scope.md and voice-guide.md entirely.

## The scope seam (live mode only)

Read scope.md before any live package input. Enforce its target repository and house rules; a fork is the source of the PR, not an alternate target. Refuse to grade a candidate targeting a different repository. If the Repo line still contains an unfilled placeholder, stop without grading and tell the student to fill the Repo line in scope.md with their section's Path Review repository. Never guess the scope. Refusals are not a completed verdict. In eval mode ignore this file entirely.

## The voice seam (live mode only)

After scope, read voice-guide.md. Check only outgoing PR title and description against its rules. In the readable summary identify each broken rule and the exact draft text that breaks it; if none break, say so. Voice findings alone do not change the verdict, because this rubric has no personal-voice check. Grade factual accuracy and required disclosure under the rubric regardless of personal style. In eval mode ignore this file entirely.

## Component reads

Preserve the fixed layout: SKILL.md, rubric.md, procedure.md, voice-guide.md, scope.md, and references/evidence-guide.md, plus the unchanged staff CONTRACT.md. Read rubric.md for checks, weights and the verdict rule; read references/evidence-guide.md for the locations and quality of each evidence family; execute procedure.md as written. Refuse to grade if rubric.md has no authored checks or verdict rule, or procedure.md has no authored operating steps: headings and template comments do not count as content. Report any missing component or procedure gap; never silently invent checks, evidence sources, or steps around it. If a gap prevents a required check, retain an unclear grade and hold under the existing rule, or refuse when the components themselves are empty.

## Verdict and output

Use exactly the binary verdict accept (ready to submit) or reject (hold). A reservation belongs in a check's evidence, never in a third verdict, score, or conditional acceptance. Give a readable per-check summary with evidence first. End the completed grading reply with the fenced JSON block below, valid and last, with nothing after it. Preserve its keys and ordering; instantiate one checks entry per rubric row in rubric order, with only pass, fail, or unclear as its grade. Do not add fields.

```json
{
  "item": "<PR URL or bundle id>",
  "checks": [
    {"name": "<check name>", "grade": "pass|fail|unclear",
     "evidence": "<one line: the fact or quote that decided it>"}
  ],
  "verdict": "accept|reject"
}
```

## Grading discipline

Name the deciding fact or quote for every check; 'looks fine' is not evidence. Grade the thing, not the polish: neither long prose nor many commits prove readiness, and terse complete work can pass. Apply each stated pass condition even when your intuition disagrees; revise a tool later, never its rule mid-run. Let the rubric decide the verdict and the procedure decide how the evidence is gathered. Treat unclear as the rubric directs; if the rule is silent, an unverifiable claim fails. Do not infer a missing run from a test added to the diff, infer human review from AI disclosure, or turn an explicitly reported limitation into an undisclosed full-success claim.

An explanation cannot waive an explicit repository prohibition or mandatory gate. Before a live PR exists, future CI is a disclosed pending step; after it exists, a stated green-CI review/submission gate requires observed green checks.

# Procedure: how this tool grades a PR package

## 1. Read order

1. Select one package and mode. In live mode read scope.md first and refuse out-of-scope work or an unfilled Repo line; then read voice-guide.md. In eval mode read neither and use only the supplied bundle.
2. Read rubric.md and this procedure for authored content; stop if either is empty. Read references/evidence-guide.md. Report any missing component or uncovered step instead of creating an unstated rule.
3. Read repo facts, the issue and thread, then the accepted plan and repro before the diff or promotional description. Record the issue trigger, expected result, scope and exclusions, test plan, deviations, explicit maintainer direction, template asks and policy. Live sources are the named plan.md, issue thread, PR template and contributing file specified by the frame.
4. Read all committed changes and commits, then pr_draft.md/title and description, then test_evidence.md or their bundled equivalents. In live mode obtain git diff main...HEAD, git log main..HEAD --oneline, and git status --short. Record the base and head; uncommitted edits are not proof of the committed PR. Read the plan first so the candidate's confidence cannot redefine its scope.

## 2. Evidence gathering

1. For Plan fidelity build a paired list: each promised outcome/file and its implementing hunk, and each changed hunk/file and its plan allowance or recorded deviation. Compare the title/description's specific fidelity and coverage claims with that list. Record both omissions and additions, including promised documentation and controls.
2. For Reproduction and controls pair the accepted trigger and expected-after with the actual before/after observations and regression assertions. Record environment/commands or described actions, visible behavior, controls, and disclosed limits. Distinguish a test assertion from an assertion-shaped comment and a typed success claim from an observed result.
3. For Repository checks list each applicable stated command/gate beside its actual run and outcome, including exits, counts, errors, skips or 'not run' reasons where supplied. Do not infer execution from a test file, PR checkbox, or generic assurance. Frozen concrete command/result summaries count; literal raw logs are not universally required.
4. For Diff quality identify the fix and supporting tests, then inspect every remaining hunk and commit for unrelated edits or residue. A disclosed deviation can explain scope, but does not automatically make unrelated churn reviewable.
5. For Standards and communication pair each stated template/policy/thread ask with its concrete answer or supporting artifact. Check issue linkage, required changelog/docs, AI disclosure and any review conditions explicitly. Do not add requirements from personal taste. For Review navigation identify the described trigger, change and pointer to evidence. In live mode separately record outgoing voice-rule breaches with their quotes.

## 3. Check execution

1. Grade every row in rubric order using only its pass condition and the paired facts already gathered. Re-read the relevant paired source whenever a fact conflicts; do not re-read unrelated material without a reason.
2. Assign pass when the condition is supported, fail when a fact contradicts it or a mandatory item is absent, and unclear when the necessary source is unavailable or ambiguous. Give each check one concrete deciding fact or short quote, including a path/section where helpful. Missing evidence never becomes an assumed pass.
3. Read honest limitations against each check's actual rule: a justified scope deferral with matching description can pass, but a wrong-trigger test or a falsely claimed suite cannot. Do not silently strengthen a check to demand every conceivable test, raw log, template spelling, or public CI before a PR exists.
4. Execute all rows even after a required failure. Report any procedural gap without improvising around it, retaining unclear for an affected required check. Keep live voice findings separate because they alone do not decide this rubric.

## 4. Verdict assembly

1. Apply the rubric's verdict rule exactly: all required checks must pass for accept; required fail or unclear means reject; preferred grades never change the verdict.
2. State the result and a readable summary for every check. On reject, lead with the first failing or unclear required check in rubric order and quote its deciding fact; list the remaining failures too. On accept, identify the evidence for the bounded delivered result and any disclosed limits without inventing reservations as a third verdict.
3. In live mode include voice findings and any pending CI gate in the summary. End with the exact frame's JSON shape: item, checks in rubric order with name/grade/evidence, verdict. Make it the last fenced JSON block with nothing after it. Never include a score or extra fields.

# Evidence guide: where evidence lives in a PR package

## Plan fidelity (harness category: silent-drift)

In eval mode read Plan context for accepted reproduction, scope pair, named files, promised tests/docs, exclusions and deviation notes; compare Candidate PR / Diff and Commits, then Title and Description. In live mode read the named plan.md including Deviations, the real issue thread (including the student's posted plan), git diff main...HEAD and git log main..HEAD --oneline, then the first line and body of pr_draft.md. Verify all files and outcomes in both directions. A smaller result with a justified plan deferral and accurate PR wording can be ready; an unexplained extra refactor, missing promised documentation, or 'implements exactly' contradicted by the diff is silent drift.

## Test evidence (harness category: not-tested)

In eval mode read Plan context's repro and test plan against Candidate PR / Test evidence, test hunks in Diff, and Repo facts' required checks. In live mode pair plan.md and William's real reproduction thread with test_evidence.md's captured commands, environment, baseline/head, stdout/stderr and exits; inspect the regression assertions in the committed diff and commands in docs/CONTRIBUTING.md/Makefile. Good evidence uses the same trigger, shows the failure before and expected changed behavior after, and records relevant controls and repository-check outcomes. A concrete named suite/result summary in a frozen bundle counts even without raw logs. A wrong-trigger happy path, a comment pretending to assert, unexplained 'all tests pass', or tests merely added does not. Preserve attempted-run failures and no-tests-collected outcomes honestly. Do not count generated mock output as observed evidence or require live reruns of frozen bundles.

## Diff quality (harness category: unreviewable)

In eval mode use Candidate PR / Diff and Commits, paired with Plan context; in live mode use the complete three-dot committed diff and commit list, with git status --short exposing uncommitted work outside that package. Good changes keep the fix, regression tests and required supporting artifacts visible. Find debug prints, dead experiments, commented code, incidental formatting and drive-by refactors by reading the hunks themselves. A small diff can still hide a harmful change; multiple focused commits can be reviewable. Do not demand squashing or extra cleanup unless the repo states it.

## Standards and comms (harness category: standards-wall)

In eval mode Repo facts supplies the captured PR-template asks, contributing policy and AI rules; Issue/Thread highlights supplies explicit direction; Candidate PR / Description and Diff show compliance. The snapshot wins over today's external repository; no live fetch is permitted. In live mode read .github/PULL_REQUEST_TEMPLATE.md and docs/CONTRIBUTING.md on the target baseline plus the full issue thread, then pr_draft.md and committed required artifacts. Check meaningful answers to every applicable ask, issue number, actual test outcomes, required docs/changelog, and truthful AI disclosure. Explained N/A and substantively equivalent concise wording can satisfy an ask; blank boilerplate cannot. Do not invent an AI ban or a human-review statement. Before opening, leave CI unchecked and state that it has not yet run; after opening inspect actual checks when policy requires them. Personal voice lives only in voice-guide.md and is reported separately in live mode. Universal review navigation uses the candidate title and description to locate the trigger, result and evidence; factual coverage claims are assessed under Plan fidelity.

# Contributing to PathReview

Thank you for contributing to PathReview! This guide explains our development workflow and standards.

## Getting Started

1. **Fork** the repository and clone your fork
2. **Set up** your development environment following [SETUP.md](SETUP.md)
3. **Browse issues** and find one that interests you
4. **Comment** on the issue to let others know you're working on it

## Branch Naming Convention

Create a branch from `main` using this format:

```
<type>/<issue-number>-<short-description>
```

Where `<issue-number>` is the GitHub issue number (the number shown under the issue title in the tracker — e.g., `#54`).

Examples:
- `fix/54-resume-section-whitespace`
- `feat/26-safety-event-health-check`
- `test/44-review-service-coverage`
- `docs/11-hybrid-scoring-formula`

Types: `fix`, `feat`, `test`, `docs`, `refactor`, `perf`, `chore`

## Commit Message Convention

We use [Conventional Commits](https://www.conventionalcommits.org/). Every commit message must follow this format:

```
<type>(<scope>): <description>

[optional body]

[optional footer]
```

**Types:** `fix`, `feat`, `test`, `docs`, `refactor`, `perf`, `chore`, `ci`

**Scopes:** `ingestion`, `rag`, `agent`, `safety`, `api`, `frontend`

**Examples:**
```
fix(ingestion): handle leading whitespace in resume section detection

Section headings with leading whitespace were not recognized, so their
content was silently dropped. Strip the line before matching headings.

Fixes #54
```

```
test(agent): add unit tests for readme_scorer tool
```

## Pull Request Process

1. **Ensure your code passes all checks:** `make check && make test-unit`
2. **Push your branch** and open a PR using the PR template
3. **Confirm CI is green on your PR** — see [CI must be green](#ci-must-be-green) below
4. **Fill out the PR template completely** — incomplete PRs will be sent back
5. **Respond to review feedback** within 48 hours
6. **Squash fixup commits** before final merge if requested

## CI must be green

**A PR with red CI is not ready for review, and green CI is part of the
submission requirement for graded work.** All five jobs must pass: `lint`,
`typecheck`, `test-unit`, `test-integration`, and `frontend`.

`main` is kept green on purpose. That means a red X on your PR is a real signal:
something in *your* change broke, not pre-existing noise. If a job fails and you
cannot connect it to your own diff, say so in the PR rather than ignoring it.

Reproduce the same five checks locally before pushing:

```bash
make lint        # ruff
make format      # black (writes changes)
make typecheck   # mypy
make test-unit   # pytest tests/unit
cd frontend && npm ci && npm test -- --run
```

### Your first PR may need a maintainer to start CI

Workflows on pull requests from forks are gated by GitHub. If your account is new
to GitHub, your first PR will sit at "waiting for approval to run workflows" until
a maintainer releases it. That is expected, and it is not a problem with your
branch. Everyone else's fork PRs run automatically. Ping the course Discord if a
run stays queued.

### Working on a seeded bug: remove its xfail marker

Many issues in the tracker are deliberately-planted bugs, and each one has unit
tests that currently fail. Those tests are marked so the suite can stay green:

```python
@pytest.mark.xfail(strict=True, reason="issue #56: structural chunker drops heading-less docs")
def test_document_with_no_headings(self, chunker):
    ...
```

The marker is `strict=True`, so **when your fix makes the test pass, CI fails
with `XPASS(strict)` until you delete the marker.** That is intentional:
removing the `@pytest.mark.xfail` line is part of fixing the issue. Your PR for
issue #56 should both fix the bug and drop the marker from every test that
covers it.

The same applies to the baseline suppressions in `pyproject.toml`. Some seeded
bugs are also flagged by ruff or mypy and are suppressed there with a comment
naming the defect — for example `api/routes/health.py` `attr-defined` is
issue #62. If you fix one of those, remove its suppression too.

### Do not bulk-fix lint or type findings

Two things will damage the course material, so please avoid them:

- **Never run `ruff check --fix --unsafe-fixes`.** The unsafe fixes rewrite
  unused variables and loop bindings, which is precisely how several seeded
  bugs are expressed. Deleting them deletes the exercise.
- **Don't "clean up" a line marked `# noqa: <RULE>` with a comment explaining
  it.** Those annotations are deliberate. A plain `# noqa` you added yourself to
  silence your own new finding is a different matter — fix the finding instead.

If you want to reduce the baseline debt, that is welcome, but do it as its own
focused PR (one rule at a time) rather than folding it into a bug fix.

## Code Style

- **Python:** Formatted with `black`, linted with `ruff`, type-checked with `mypy`
- **TypeScript/React:** Follows the existing component patterns in `frontend/src/`
- **Tests:** Every code change should include or update relevant tests
- **Docstrings:** All public functions and classes must have Google-style docstrings

## Running Checks Locally

```bash
make lint       # Ruff linter
make format     # Black formatter
make typecheck  # Mypy type checker
make check      # All three
make test-unit  # Unit tests
```

## Adding a New Parser

If your issue involves adding a new document parser to the ingestion pipeline:

1. Create a new file in `ingestion/parsers/` (e.g., `web_parser.py`)
2. Implement the `BaseParser` interface:
   ```python
   from ingestion.parsers.base import BaseParser, ParseResult

   class WebParser(BaseParser):
       def parse(self, content: str | bytes) -> ParseResult:
           ...
   ```
3. Register the parser in `ingestion/pipeline.py`
4. Add unit tests in `tests/unit/test_<parser_name>.py`
5. Add a sample fixture in `tests/fixtures/` if needed

## Adding a New Agent Tool

If your issue involves adding a new tool to the agent system:

1. Create a new file in `agent/tools/` (e.g., `dependency_audit_tool.py`)
2. Implement the `BaseTool` interface:
   ```python
   from agent.tools.base import BaseTool, ToolResult

   class DependencyAuditTool(BaseTool):
       name = "dependency_audit"
       description = "Checks for outdated dependencies in project repos"

       def execute(self, input_data: dict) -> ToolResult:
           ...
   ```
3. Register the tool in `agent/orchestrator.py`
4. Add unit tests in `tests/unit/test_<tool_name>.py`
5. Add mock responses in `tests/fixtures/` if the tool calls external APIs

## Questions?

Open a discussion or reach out in the course Discord channel.
